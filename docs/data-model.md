# Модель данных 6d7

Решения по хранению данных. Обсуждение и ответы — в [QnA.md](QnA.md).

Данные делятся на две части: **встроенные** (правила игры, математика, виды, классы, картинки — одинаковые для всех и не настраиваются) и **пользовательские** (кампании, карты, фишки, листы, медиафайлы мастера и игроков).

## 1. Встроенные данные — пакет правил

Неизменяемый пакет с номером версии, собранный из `dnd-db/data`. Клиент скачивает его один раз и кэширует по хэшу.

```
rules/<версия>/
  index.json        версия, хэши частей, источники
  core.json         механика: классы, виды, черты, снаряжение, магпредметы, существа, спутники, таблицы
  spells.json       механика заклинаний
  text.ru.json      названия и описания по id (язык — подменой файла)
  search.ru.json    готовый индекс поиска: нормализованные имена ru/en → id
media/<хэш>.webp    иконки предметов и заклинаний, токены NPC (для сеток — атласы)
```

- Id постоянные (`fireball`, `longsword-plus-1`). Переименования — через таблицу псевдонимов (как `spell_aliases`).
- Индексы (заклинания по спискам и кругам, предметы по категориям, поиск) считаются при сборке, а не на телефоне.
- Пакет на открытый и закрытый пока не делится.
- Логика правил (`derive`, `levelup`, `rest`, `uses`, `wildshape`, `companion`, `vision`) — чистый TypeScript без интерфейса, общий для клиента и сервера. Она живёт в пакете `dnd-rules` (подмодуль в корне репозитория; 6d7 берёт её через псевдоним `@rules`, базу — `@rules-data`, тип листа — `dnd-sheet`) вместе с базой, типом листа и иконками; старый лист пока держит свою копию в `app/src`.
- Производные значения (обзор, свет, бонусы магических предметов) не хранятся: их считает эта логика.

Почему JSON: вся база — 2,3 МБ, в brotli — 267 КБ, разбор всех файлов на ПК — 16 мс (на телефоне порядка 50–100 мс), один раз за сессию. В работе читаются объекты в памяти с индексами.

## 2. Пользовательские данные — документы

| Документ | Что внутри | Кто пишет |
|---|---|---|
| `campaign` | название, настройки, игроки (имя, цвет), порядок карт, сохранённые NPC | мастер в редакторе |
| `map/<id>` | картинка, сетка, условия, стены, двери, спавн, расставленные NPC, туман из редактора | мастер в редакторе |
| `game` | активная карта | игра |
| `game/map/<id>` | открытые двери, фишки, перемещённые, добавленные и удалённые в игре NPC, рисунки, открытый туман, туман мастера в игре | игра |
| `seat/<id>` | всё игрока: лист, спутник, инвентарь, заклинания, ячейки, ресурсы, портрет | игрок и мастер |
| `media/<хэш>` | оригиналы карт, тайлы, портреты | все; файл не меняется |

- У каждого объекта постоянный id (UUIDv7, генерируется на клиенте) и номер правки.

### Как сделано (этап 1, `6d7/src/campaign`)

- `campaign` (`types.ts`): название, `settings` (свободное перемещение, свободное открытие дверей, динамический туман), `players` (id, имя, цвет — первый свободный по порядку `flow`), `maps` (порядок id карт; первая даёт картинку плитки), `npcs` (сохранённые NPC: id, токен каталога, имя, описание). Изменения — операции `CampaignOp`.
- `map/<id>` — `MapScene` модуля карты. `rules` хранит только то, что карта поменяла в настройках кампании (как переопределения у экземпляра в Figma); действующие условия — `rulesOf(карта, настройки кампании)`; «Свободное открытие дверей» работает только при свободном перемещении. У картинки — `original` (загруженный файл) и `preview` (плитка главного экрана), оба — ссылки `media:<sha256>`. У мазков тумана — id. У NPC на карте — `token` (id токена каталога) и `saved` (id сохранённого NPC кампании, если мастер сделал его уникальным); картинка NPC каталога не хранится: карта находит её по `token` там, где открыта (адрес на dev-сервере и на сайте разный), а адрес в `image`, записанный прежними версиями, не используется. Картинка, которая не загрузилась, заменяется первой буквой имени. Название карты меняет операция `name`.
- `seat/<id игрока>` — лист игрока (раздел 5). Правки игрока пишутся в него сразу и в историю редактора не попадают. Правка листа — по полям (`{ doc: 'seat/<id>', op: SeatPatch }`, `6d7/src/game/seat/patch.ts`): поля листа по одному (`sheet` — заданные, `cleared` — стёртые), заклинания, ячейки предметов и спутник — частью целиком. Две правки разных полей одновременно (игрок печатает, мастер нажал «Отдых для всех») не затирают друг друга; в журнал и сеть уходит только изменённое.
- Одна сохраняемая правка — `Change`: операция над документом, документ целиком (`set`) или его удаление (`drop`). Журнал, «Отменить» и потом сеть работают с ними.
- В браузере (IndexedDB `6d7-campaigns`): `docs` — снимки документов, `journal` — правки после снимка (у каждой вкладки свои ключи `[кампания, вкладка, номер]` и время правки: редактор и игра игрока в соседних вкладках не затирают друг друга; кампания, открытая с журналом, сначала записывается снимком), `meta` — сводка для главного экрана (название, игроки, картинка первой карты, время; для удаления данных не используется), `tiles` — тайлы картинок, `codes` — коды-заглушки игроков. Медиа — отдельно, `6d7-media`. До переименования приложения базы назывались `vtt-campaigns` и `vtt-media` (язык — `vtt-language` в `localStorage`): при первом открытии содержимое старой базы переносится в новую той же транзакцией, что её создаёт (прерванный перенос повторится), затем старая база удаляется.
- Кампания открыта только в одной вкладке (`6d7/src/campaign/local/lock.ts`, Web Locks, замок `6d7:campaign:<id>`): вкладка, которая держит кампанию, по просьбе другой («Открыть здесь») записывает несохранённое и отпускает её; главный экран переименовывает и удаляет только свободную кампанию. Без Web Locks (старый браузер, dev-сервер по http в локальной сети) вкладки не разделяются.
- Тайлы удаляются, когда картинку не использует ни одна карта — ни редактора (`map/<id>`), ни игры (`game/map/<id>`: сцена и база слияния), ни правка в журнале. Это проверяется по самим документам в одной транзакции с удалением (при открытии кампании, без ожидания, и при её удалении). Если тайлов картинки нет, а оригинал в медиа есть (тайлы убрали, пока картинку ещё показывала отмена или другая вкладка), картинка режется заново под тем же id при первом показе.
- Ошибка записи (браузер отказал, кончилось место) не теряет правки: документы остаются несохранёнными и пишутся снова через 10 с или по «Сохранить»; редактор и игра мастера показывают плашку, щелчок по ней повторяет запись. Транзакция, в которой что-то бросило исключение, откатывается целиком.
- Коды игроков — 6 знаков без похожих (0/O, 1/I/L), уникальные в браузере, в архив не попадают; импорт выдаёт новые.
- Игра хранится **поправками** к объектам кампании. При запуске игры: кампания последней версии + поправки сохранения. Поправка применяется, если мастер не правил объект в редакторе после сохранения игры.
- Слияние один раз, при запуске: пока мастер в редакторе, игра остановлена.
- Как сделано (этап 8, `6d7/src/campaign/game.ts`): `game` — `{ active }` (активная карта); `game/map/<id>` — `{ scene, base }`: карта, как она в игре, и карта редактора, с которой её слили в прошлый раз (вместо номеров правок — трёхстороннее слияние по объектам: изменённое редактором после `base` — из редактора, остальное — из игры; добавленное игрой остаётся, удалённое редактором уходит; новый туман редактора ложится после тумана игры); `game/explored/<id>` — маска открытого `{ w, h, data }` (байт на точку, 512 точек по длинной стороне; `6d7/src/map/core/explored.ts`). Правки карты игры — те же `MapOp` в журнале (`{ doc: 'game/map/<id>', op }`), история «Отменить» их не пишет; маска пишется целиком в паузах.
- Маска открытого считается по операциям карты, а не при отрисовке (`6d7/src/map/core/exploring.ts`, `trackExplored`): после каждой операции, которая двигает фишки игроков или меняет то, что закрывает обзор, открывается видимое; новый туман закрывает, «Залить» закрывает всё, карта без тумана забывает открытое. Маску активной карты держит вкладка мастера (`game/master/explored.ts`, `ExploredKeeper`), что бы ни было на экране (предпросмотр другой карты, вкладка в фоне), и пишет её в паузах; маску, записанную другим (запуск игры со слиянием, импорт состояния), берёт вместо своей. Вкладка игрока считает ту же маску сама по тем же операциям. Движок карты только показывает маску.
- На сервере у документа — снимок и журнал операций (как `MapOp`); сохранение игры — точка в журнале. По сети ходят те же операции. Права — по документам: игрок пишет в свой `seat` и в разрешённые ему игровые операции.
- Каждая часть знает версию своей схемы; цепочка миграций открывает старые архивы.

### Автосохранение

Каждое действие сохраняется само — и в браузере, и потом на сервере. Сохраняется не документ целиком, а операция: она дописывается в журнал документа (150 байт — стена, около 3 КБ — мазок тумана на 200 точек). Снимок документа пишется, когда мастер перестал работать на несколько секунд, или каждые несколько сотен операций; после этого журнал до снимка удаляется.

Почему не снимок на каждое действие: большая карта (2000 стен, 200 дверей, 100 NPC, 300 мазков тумана) — около 1 МБ JSON и 8 мс на сериализацию; на каждое действие это заметные подёргивания. Журнал операций стоит меньше 1 мс на действие.

- Пока сервера нет — журнал и снимки в IndexedDB браузера.
- С сервером журнал — это те же операции, которые и так идут по сети; сервер дописывает их и иногда делает снимок.
- История «Отменить / Повторить» живёт только в открытом редакторе и в архив не попадает.

### Игра между вкладками (этап 9)

Вкладка мастера держит игру, как потом сервер (`6d7/src/game/net/protocol.ts`, канал — `link.ts`):

| Кто | Сообщение | Что значит |
|---|---|---|
| мастер → всем | `host` / `end` | игра открыта (ждущие игроки здороваются снова) / мастер ушёл |
| игрок → мастеру | `hello {tab, player}` | вкладка игрока подключается |
| мастер → вкладке | `welcome {campaign, seat, map}` | название, игроки, настройки, лист игрока, карта игры с открытым туманом |
| мастер → всем | `map`, `op {map, op, from}` | игра перешла на другую карту; правка карты игры (`from` — вкладка, у которой она уже есть) |
| игрок → мастеру | `playerOp`, `playerSeat`, `roll` | правка карты (мастер проверяет права), новый лист, бросок для лога мастера |
| мастер → всем | `seat {player, seat, from}`, `resync`, `gone` | лист изменился; правка отклонена — карта заново этой вкладке; места игрока больше нет |

Правка карты — та же `MapOp`, что в журнале; открытый туман каждая вкладка считает сама по фишкам, целиком маска приходит только с картой.

### Слияние правок редактора с игрой

| Мастер в редакторе | В игре |
|---|---|
| добавил стены, двери, NPC, карты | появятся |
| удалил объект | исчезнет вместе с игровым состоянием |
| передвинул или переименовал NPC | правка редактора важнее игровой позиции |
| поменял сетку | фишки и NPC по сетке остаются в своих клетках |
| заменил картинку | фишки остаются в клетках; открытый туман (в долях картинки) остаётся при тех же пропорциях, при других — сбрасывается |
| закрасил туман поверх открытого | место закрывается снова |
| поменял настройки | действуют сразу |

В редакторе мастер может править и состояние «как сейчас в игре» (импорт сохранения в редактор) — на свою ответственность.

## 3. Форматы

| Данные | Формат |
|---|---|
| Правила | JSON, сжатый brotli, кэш по хэшу |
| Кампания, карты, листы, игра | JSON; на сервере — снимок + журнал операций |
| Операции по сети | JSON за сменяемым кодеком (при нужде — MessagePack); перетаскивание фишки — 20–30 сообщений в секунду |
| Туман, рисунки | двоичные массивы: маска тумана — байт на точку низкого разрешения, сжатая; линии — целые числа с разностями |
| Картинки | файлы WebP/AVIF и оригинал, адрес по SHA-256; никогда не base64 в JSON |

Двоичные форматы окупаются там, где данные — массивы чисел; для структурных данных встроенный `JSON.parse` быстрее большинства двоичных декодеров на JS.

## 4. Архив кампании

ZIP с расширением `.6d7` (по названию приложения); части читаются отдельно.

```
manifest.json            версия схемы, версия правил, правка кампании, хэши частей
campaign.json
maps/<id>.json           + maps/<id>.fog.bin
game/state.json          + game/<id>.reveal.bin, game/<id>.drawings.bin
seats/<id>.json
media/<хэш>.<расширение>
tiles/<id картинки>/…    если архив с тайлами весит мегабайты; иначе только оригиналы
```

- «Экспортировать» — весь архив; «Экспорт состояния игры» — `game/`, `seats/` и их медиа.
- Сделано (этап 8): `game/state.json`, `game/maps/<id>.json` (`{ scene, base }`), `game/<id>.explored.bin` (байты маски; размеры — в `manifest.game.explored`). Архив состояния игры — тот же формат с `manifest.kind: 'game'`, без кампании и карт; принимается только в свою кампанию (`manifest.campaign`). Рисунки пока внутри карты игры, отдельного `drawings.bin` нет.
- Коды игроков в архив не попадают: каждый импорт в редактор выдаёт новые.

Сделано (`6d7/src/campaign/archive.ts`): `manifest.json` — формат `6d7`, версия схемы, id и название кампании, дата, списки карт, листов, медиа и картинок с тайлами; документы — JSON (туман пока внутри `maps/<id>.json`, двоичный — вместе с игрой); медиа и тайлы (`tiles/<id картинки>/<уровень>/<столбец>-<строка>.webp`) — без сжатия, JSON — deflate. Тайлы кладутся, если архив с ними не больше 50 МБ; у картинки без оригинала — всегда. Импорт: картинка без тайлов режется заново из оригинала под тем же id. Архив другого формата, более новой версии или повреждённый — понятная ошибка.

## 5. Лист игрока (`seat`) — сделано

Модуль `6d7/src/game/seat/seat.ts`, правки по полям — `patch.ts`. Между вкладками: вкладка игрока шлёт мастеру правку полей через 300 мс после последнего нажатия (и не реже раза в секунду, пока печатает), мастер записывает её, отправляет остальным вкладкам этого игрока и в ответ шлёт только то, что изменил сам (отдых, свои правки на странице игрока); приветствие несёт лист целиком. Схема 1:

```ts
interface Seat {
  schema: 1
  sheet: DnDCharacter          // свободные поля листа, все редактируемые; в них же ресурсы (resources),
                               // истощение (exhaustion), ячейки (lvlNSpellSlots*, pactSlot*), облики (wildShape)
  spells: { id: string; prepared?: boolean; tag?: string; name?: string; level?: number }[]  // id из базы или 'custom-…'
  inventory: ({ uid: string; item?: string; name?: string; equipped?: boolean; attuned?: boolean } | null)[]  // 72 ячейки
  companion: Record<string, string | boolean | undefined> | null   // лист спутника
  started?: boolean            // игрок нажал «Начать игру»: дальше вход по коду ведёт сразу на поле
}
```

- Картинки — поля листа со ссылкой `media:<sha256>`: портрет `appearance`, эмблема `factionImg`, картинка спутника `portrait`. При загрузке картинка уменьшается до 512 px по большей стороне и кодируется в WebP (JPEG, если браузер не пишет WebP); хранилище — `6d7/src/game/media/media.ts` (сейчас IndexedDB браузера, потом сервер). Для игрока всё как раньше: щелчок по месту портрета и картинка на листе.
- Уборка медиа (при открытии кампании, без ожидания, и при её удалении): ссылки `media:` ищутся во всех документах, журналах и сводках. Файл, на который никто не ссылается, сначала помечается и удаляется только через сутки, если ссылки так и не появились (успевают сохраниться только что загруженный портрет и картинка, которую вернёт «Отменить» открытого редактора); на файл снова сослались — пометка снимается. Файлы удалённой кампании уходят сразу, если их не использует другая. Отказ браузера записать файл — ошибка для того, кто загружает (ссылки в никуда не бывает); без IndexedDB (приватное окно) файлы живут в памяти до закрытия вкладки, иначе в памяти их не держат.
- Заклинания — по id базы; название берётся из базы на языке интерфейса. Своё заклинание — `custom-<uuid>` с названием и кругом.
- Слотов героя нет: ячейки с отметками «экипировано» и «настроено». Для логики правил (`@rules`, плоский лист старого приложения) `characterOf` собирает его плоский лист: надетые доспех, щит и оружие встают в места героя, поэтому КД и бонусы магических предметов считаются по-старому; `withCharacter` забирает изменения обратно.
- Обзор (тёмное зрение, обзор в темноте и на свету) не хранится: его считает `dnd-rules/src/rules/vision.ts` по виду, умениям, воззваниям и надетым предметам; в листе это нередактируемые поля.
- Лист старого приложения переносится `importCharacter` (`seat/import.ts`): заклинания по названиям → id, слоты `worn` → экипированные ячейки, картинки из data URL → хранилище. Обратно — `exportCharacter` (`seat/export.ts`): «Экспорт листа» скачивает JSON старого приложения с картинками внутри (data URL), его же принимает «Импорт листа».
- Фишка игрока на карте — `Token` с `kind: 'player'` и id игрока; фишка спутника — id `<игрок>:companion` и `owner` = id игрока (ею двигает тот же игрок). Имя, портрет, цвет и тёмное зрение фишка берёт из листа.
- Действия игрока — `seat/actions.ts`: получить, купить, экипировать, настроить, удалить предмет; изучить, подготовить, забыть заклинание; ячейки. В поиске заклинаний — только списки классов персонажа до его высшего круга ячеек; заклинания, которые держат подготовленными подкласс, вид или умение класса («Метка охотника» у Избранного врага), в лимит подготовленных не входят.
