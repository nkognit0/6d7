# Модель данных VTT

Решения по хранению данных. Обсуждение и ответы — в [QnA.md](QnA.md).

Данные делятся на две части: **встроенные** (правила игры, математика, виды, классы, картинки — одинаковые для всех и не настраиваются) и **пользовательские** (кампании, карты, фишки, листы, медиафайлы мастера и игроков).

## 1. Встроенные данные — пакет правил

Неизменяемый пакет с номером версии, собранный из `dnd-db/data`. Клиент скачивает его один раз и кэширует по хэшу.

```
rules/<версия>/
  index.json        версия, хэши частей, источники
  core.json         механика: классы, виды, черты, снаряжение, магпредметы, существа, спутники, таблицы
  spells.json       механика заклинаний
  text.ru.json      названия и описания по id (язык — подменой файла)
  search.ru.json    готовый индекс поиска: нормализованные имена ru/en → id
media/<хэш>.webp    иконки предметов и заклинаний, токены NPC (для сеток — атласы)
```

- Id постоянные (`fireball`, `longsword-plus-1`). Переименования — через таблицу псевдонимов (как `spell_aliases`).
- Индексы (заклинания по спискам и кругам, предметы по категориям, поиск) считаются при сборке, а не на телефоне.
- Пакет на открытый и закрытый пока не делится.
- Логика правил (`derive`, `levelup`, `rest`, `uses`, `wildshape`, `companion`, `vision`) — чистый TypeScript без интерфейса, общий для клиента и сервера. Сейчас она живёт в `app/src`, VTT берёт её через псевдоним `@app`; при создании репозитория VTT её стоит вынести в общий пакет.
- Производные значения (обзор, свет, бонусы магических предметов) не хранятся: их считает эта логика.

Почему JSON: вся база — 2,3 МБ, в brotli — 267 КБ, разбор всех файлов на ПК — 16 мс (на телефоне порядка 50–100 мс), один раз за сессию. В работе читаются объекты в памяти с индексами.

## 2. Пользовательские данные — документы

| Документ | Что внутри | Кто пишет |
|---|---|---|
| `campaign` | название, настройки, игроки (имя, цвет), порядок карт, сохранённые NPC | мастер в редакторе |
| `map/<id>` | картинка, сетка, условия, стены, двери, спавн, расставленные NPC, туман из редактора | мастер в редакторе |
| `game` | активная карта | игра |
| `game/map/<id>` | открытые двери, фишки, перемещённые, добавленные и удалённые в игре NPC, рисунки, открытый туман, туман мастера в игре | игра |
| `seat/<id>` | всё игрока: лист, спутник, инвентарь, заклинания, ячейки, ресурсы, портрет | игрок и мастер |
| `media/<хэш>` | оригиналы карт, тайлы, портреты | все; файл не меняется |

- У каждого объекта постоянный id (UUIDv7, генерируется на клиенте) и номер правки.
- Игра хранится **поправками** к объектам кампании. При запуске игры: кампания последней версии + поправки сохранения. Поправка применяется, если мастер не правил объект в редакторе после сохранения игры.
- Слияние один раз, при запуске: пока мастер в редакторе, игра остановлена.
- На сервере у документа — снимок и журнал операций (как `MapOp`); сохранение игры — точка в журнале. По сети ходят те же операции. Права — по документам: игрок пишет в свой `seat` и в разрешённые ему игровые операции.
- Каждая часть знает версию своей схемы; цепочка миграций открывает старые архивы.

### Автосохранение

Каждое действие сохраняется само — и в браузере, и потом на сервере. Сохраняется не документ целиком, а операция: она дописывается в журнал документа (150 байт — стена, около 3 КБ — мазок тумана на 200 точек). Снимок документа пишется, когда мастер перестал работать на несколько секунд, или каждые несколько сотен операций; после этого журнал до снимка удаляется.

Почему не снимок на каждое действие: большая карта (2000 стен, 200 дверей, 100 NPC, 300 мазков тумана) — около 1 МБ JSON и 8 мс на сериализацию; на каждое действие это заметные подёргивания. Журнал операций стоит меньше 1 мс на действие.

- Пока сервера нет — журнал и снимки в IndexedDB браузера.
- С сервером журнал — это те же операции, которые и так идут по сети; сервер дописывает их и иногда делает снимок.
- История «Отменить / Повторить» живёт только в открытом редакторе и в архив не попадает.

### Слияние правок редактора с игрой

| Мастер в редакторе | В игре |
|---|---|
| добавил стены, двери, NPC, карты | появятся |
| удалил объект | исчезнет вместе с игровым состоянием |
| передвинул или переименовал NPC | правка редактора важнее игровой позиции |
| поменял сетку | фишки и NPC по сетке остаются в своих клетках |
| заменил картинку | фишки остаются в клетках; открытый туман (в долях картинки) остаётся при тех же пропорциях, при других — сбрасывается |
| закрасил туман поверх открытого | место закрывается снова |
| поменял настройки | действуют сразу |

В редакторе мастер может править и состояние «как сейчас в игре» (импорт сохранения в редактор) — на свою ответственность.

## 3. Форматы

| Данные | Формат |
|---|---|
| Правила | JSON, сжатый brotli, кэш по хэшу |
| Кампания, карты, листы, игра | JSON; на сервере — снимок + журнал операций |
| Операции по сети | JSON за сменяемым кодеком (при нужде — MessagePack); перетаскивание фишки — 20–30 сообщений в секунду |
| Туман, рисунки | двоичные массивы: маска тумана — байт на точку низкого разрешения, сжатая; линии — целые числа с разностями |
| Картинки | файлы WebP/AVIF и оригинал, адрес по SHA-256; никогда не base64 в JSON |

Двоичные форматы окупаются там, где данные — массивы чисел; для структурных данных встроенный `JSON.parse` быстрее большинства двоичных декодеров на JS.

## 4. Архив кампании

ZIP с расширением `.6d7` (по названию приложения); части читаются отдельно.

```
manifest.json            версия схемы, версия правил, правка кампании, хэши частей
campaign.json
maps/<id>.json           + maps/<id>.fog.bin
game/state.json          + game/<id>.reveal.bin, game/<id>.drawings.bin
seats/<id>.json
media/<хэш>.<расширение>
tiles/<id картинки>/…    если архив с тайлами весит мегабайты; иначе только оригиналы
```

- «Экспортировать» — весь архив; «Экспорт состояния игры» — `game/`, `seats/` и их медиа.
- Коды игроков в архив не попадают: каждый импорт в редактор выдаёт новые.

## 5. Лист игрока (`seat`) — сделано

Модуль `vtt/src/game/seat/seat.ts`. Схема 1:

```ts
interface Seat {
  schema: 1
  sheet: DnDCharacter          // свободные поля листа, все редактируемые; в них же ресурсы (resources),
                               // истощение (exhaustion), ячейки (lvlNSpellSlots*, pactSlot*), облики (wildShape)
  spells: { id: string; prepared?: boolean; tag?: string; name?: string; level?: number }[]  // id из базы или 'custom-…'
  inventory: ({ uid: string; item?: string; name?: string; equipped?: boolean; attuned?: boolean } | null)[]  // 72 ячейки
  companion: Record<string, string | boolean | undefined> | null   // лист спутника
}
```

- Картинки — поля листа со ссылкой `media:<sha256>`: портрет `appearance`, эмблема `factionImg`, картинка спутника `portrait`. При загрузке картинка уменьшается до 512 px по большей стороне и кодируется в WebP (JPEG, если браузер не пишет WebP); хранилище — `vtt/src/game/media/media.ts` (сейчас IndexedDB браузера, потом сервер). Для игрока всё как раньше: щелчок по месту портрета и картинка на листе.
- Заклинания — по id базы; название берётся из базы на языке интерфейса. Своё заклинание — `custom-<uuid>` с названием и кругом.
- Слотов героя нет: ячейки с отметками «экипировано» и «настроено». Для логики правил старого приложения (`@app`) `characterOf` собирает его плоский лист: надетые доспех, щит и оружие встают в места героя, поэтому КД и бонусы магических предметов считаются по-старому; `withCharacter` забирает изменения обратно.
- Обзор (тёмное зрение, обзор в темноте и на свету) не хранится: его считает `app/src/rules/vision.ts` по виду, умениям, воззваниям и надетым предметам; в листе это нередактируемые поля.
- Лист старого приложения переносится `importCharacter` (`seat/import.ts`): заклинания по названиям → id, слоты `worn` → экипированные ячейки, картинки из data URL → хранилище.
- Действия игрока — `seat/actions.ts`: получить, купить, экипировать, настроить, удалить предмет; изучить, подготовить, забыть заклинание; ячейки. В поиске заклинаний — только списки классов персонажа до его высшего круга ячеек; заклинания, которые держат подготовленными подкласс, вид или умение класса («Метка охотника» у Избранного врага), в лимит подготовленных не входят.
